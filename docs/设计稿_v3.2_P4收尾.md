## 0. 这一版要解决什么

v3.0 设计稿把收尾阶段（P4）定为三件事：**收件人库（跨事件复用）、执行历史查看、示例数据更新**。
前两件的数据底座在 P0–P3 里已经铺好（`lp_data/runs/` 有 Run 记录、收件人按事件存），
但**一直只有数据、没有界面**，用户实际上用不到。

### 0.1 一个必须先解决的历史约束

2026-10-23 用户反馈②明确说过：「**场景与事件 / 场景模板 / 收件人库**三个入口看不懂区别，只要事件库」，
当时把「收件人库」那个**空壳页整个删掉**了。

所以本轮**不复活独立导航页**（顶层导航仍然是「事件库 / 设置 / 帮助」三项），
收件人库改做**事件库里的第三个标签页**，与「事件」「场景模板」并列。
执行历史同理，做**第四个标签页**。用户要的是「功能」，不是「多一个入口」。

## 1. 收件人库（跨事件复用）

### 1.1 为什么需要

真实场景：同一批客户，每季度要发一次对账单。每个季度新建一个事件 → **收件人清单要重新导入一遍**。
现有「场景模板」能带出流水线、邮件模板、选项，但**收件人只能靠场景模板里存一份**，
或者手工重导 —— 没有一个「常用收件人」的地方。

### 1.2 界面

事件库 → 第三个标签页「**收件人库**」：

```
┌ 收件人库 ─────────────────────────────────────────────────────┐
│ [新增] [编辑] [删除] [从事件导入…] [添加到事件…] [导入 Excel] [导出 Excel] │
├──────────────┬──────────────┬────┬────────────┬──────────────┤
│ 收件人名称   │ To           │ 组 │ 打开口令   │ 权限口令(勿发)│
├──────────────┼──────────────┼────┼────────────┼──────────────┤
│ 苏州启衡科技 │ ir@…-demo.cn │    │ Open-1101  │ ••••         │
└──────────────┴──────────────┴────┴────────────┴──────────────┘
```

- 表格列与事件里「收件人」步骤一致（含**附件路径**列、自定义字段列），少一列「水印」。
- 工具条七个按钮：
  - **新增 / 编辑 / 删除**：与事件里的收件人编辑对话框同一套表单（同一份代码，不做第二套）。
  - **从事件导入…**：选一个事件 → 把它的收件人整个收进库（重名按名称合并）。
  - **添加到事件…**：勾选库里的收件人 → 选目标事件 → 并进去。
  - **导入 Excel/CSV / 导出 Excel**：复用事件里那套模板下载 + 三步校验流程。

### 1.3 事件工作台里的两个入口

「收件人」步骤的工具条加两个按钮（与现有按钮同排）：

- **从收件人库添加…** → 勾选库里的人 → 并入当前事件
- **存入收件人库** → 把当前事件的收件人整个存进库

### 1.4 数据模型

新增目录 `lp_data/recipients/`，每条一个 json（与 events / scenarios / runs 同级）：

```json
{
  "id": "rcp_xxxx",
  "name": "苏州启衡科技有限公司",
  "to": "ir@qiheng-demo.cn",
  "cc": "", "bcc": "", "wm": "", "group": "", "subject": "",
  "fields": {"Call_Amount": "200,000"},
  "attachments": [],
  "open_pw": "Open-1101",
  "owner_pw": "Own-2202",
  "updated_at": "2026-10-23 23:40:00"
}
```

- 复用现成的 `normalize_recipient()`，只多存 `id` 与 `updated_at`。
- **口令存在库里** → 库文件属敏感文件，和 `lp_data/` 其余部分同管控级别（界面红字提示照旧）。

### 1.5 合并规则（铁律：绝不覆盖已有口令）

按**名称**合并，与既有的 `sync_scenario_to_event()` 一致：

- 目标已存在的收件人：**保留目标的口令与自定义字段**，只补空缺（邮箱、抄送、附件路径、字段）。
- 目标没有的：直接新增。
- **绝不因为库里那份旧了就把事件里已用的口令改掉**（否则等于把已发出去的批次改了）。

### 1.6 `lp_v3.py` 新增

| 函数 | 作用 |
|---|---|
| `new_pool_recipient(rec=None)` | 新建一条库记录（带 id） |
| `normalize_pool_recipient(rec)` | 规范化（复用 `normalize_recipient`） |
| `pool_merge_recipient(pool, rec)` | 按名称合并，返回 `(pool, 是否新增)` |
| `merge_recipients_into_event(event, records)` | 把若干收件人并入事件，返回 `(event, 新增数, 更新数)` |
| `Store.list_pool()` / `save_pool_recipient()` / `delete_pool_recipient()` | 收件人库的存取 |

## 2. 执行历史查看

### 2.1 界面

事件库 → 第四个标签页「**执行历史**」：

| 列 | 来源 |
|---|---|
| 开始时间 | `run.started_at` |
| 事件 | `run.event_name` |
| 状态 | `run.status`（`ok` / `preflight_failed` / `failed`） |
| 草稿 | `len(run.items)` 中 `draft` 非空的条数 |
| 成功 / 失败 / 跳过 | `run.stats.ok / fail / skip` |
| 附件包 | `run.items[*].files` 的总数 |

双击一行 → 详情弹窗：

- 上半部分：每个收件人 / 合并组一行 —— 姓名、成员、附件包文件数、缺失文件、草稿状态、错误、口令指纹。
- 下半部分：执行日志（`run.logs`）与错误/警告清单。
- 底部按钮：**打开该事件**（跳回工作台）、**只重跑失败项**（沿用已有能力）。

事件工作台「预览与生成」步骤里也加一个「历史执行」按钮，看**本事件**的历史（按事件过滤）。

### 2.2 数据层

`Store.list_runs(event_id=None)` / `load_last_run()` 已存在且够用，本轮**不改数据层**，
只加 GUI。另外补一条：**Run 记录里的 `items[*].files` 是绝对路径**，
界面显示文件名、tooltip/详情里给完整路径。

### 2.3 状态显示口径

`run.status` 的取值见 `run_event()`：`preflight_failed`（预检没过）、`ok`（正常）。
界面把 `preflight_failed` 显示成「预检未通过」，`ok` 显示成「已完成」。

- `lp_data.example.json` 更新成 v3.1 之后的结构：示例事件带**两种条目**

## 4. 不做什么

- **不做**独立导航页（顶层仍是「事件库 / 设置 / 帮助」），理由见 §0.1。
- **不做**收件人库与事件收件人的双向自动同步（只有显式的「存入 / 添加」按钮，避免意外改动已发批次）。
- **不做**执行历史里的文件在线预览（只列文件名与路径）。
- **不做**执行历史的删除/清理功能（Run 记录是审计材料，留着）。
