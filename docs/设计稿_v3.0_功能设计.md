# v3.0 功能设计稿：事件驱动的文档分发

> 状态：待评审。本文只定义设计，不含实现。
> 背景：v2.x 的所有配置（收件人、附件、Word模板、邮件模板、水印设置）都平铺在
> 单一的 `lp_data.json` 里，**不同业务场景之间无法共存**——做第二季对账单时，
> 第一季的收件人清单、附件、模板会被覆盖或手工清空。

---

## 一、核心问题与设计目标

### 现状痛点

| 痛点 | 现状 | 影响 |
|---|---|---|
| 场景之间无隔离 | 收件人/附件/模板全是全局单份 | 并行做两个场景必然互相污染 |
| 文档与 LP 无映射 | Word 合并表、PDF 水印、加密各是独立功能 | 同一场景里"谁该拿哪个文件"靠人工记 |
| 附件不归属 | 附件路径挂在收件人行上 | 场景级附件（所有人同一份）无法表达 |
| 生成过程黑盒 | 只能一次性跑完看日志 | 出错要重跑全批 |

### 设计目标

1. **事件驱动**：一次分发 = 一个「发送事件」，拥有自己完整的收件人、附件、文档、邮件配置。
2. **场景可复用**：场景模板定义"怎么做"，事件定义"这次做给谁"。
3. **文档与 LP 强映射**：每个文档产出步骤都明确"产出给谁、字段从哪来"。
4. **一个按钮出草稿**：事件配置完成后，一键批量生成全部 Outlook 草稿。
5. **可回溯**：每次执行产出清单与结果记录，可只重跑失败项。

## 二、概念模型

```
场景 Scenario  ──模板──►  发送事件 Event  ──执行──►  执行记录 Run
（"怎么做"）              （"这次做给谁"）         （"做了啥"）
```

### 2.1 发送事件 Event（一等公民）

```
SendEvent
├── meta        : id, name, 业务类型, 截止日期, 备注, 创建时间, 状态
├── recipients  : [Recipient]        该事件的收件人清单
├── pipeline    : [Step]             文档生成流水线（有序，见 §3）
├── attachments : [Attachment]       静态附件清单（场景级/指定LP/按组）
├── mail        : {subject, body, from_addr, cc_default, bcc_default}
├── options     : {merge_groups, gp_owner_mode, gp_owner_pw, outdir, filename_tpl, wm_settings}
└── runs        : [Run]              历史执行记录
```

### 2.2 收件人 Recipient

```
Recipient
├── name        : 法定名称（也是水印文字的默认值、文件名的默认值）
├── to / cc / bcc
├── wm_text     : 水印文字（留空=用 name）
├── group       : 合并组（同组=同一封邮件，收件人合并）
├── fields      : {任意键: 值}      ★ 自定义字段，供文档映射使用
├── open_pw     : 打开口令（每人独立）
├── owner_pw    : 权限口令（每人独立，或用 GP 统一口令）
└── attachments : [path]             该 LP 专属附件
```

**`fields` 是本次重构的关键新增**。它让"文档字段"与"收件人身份"解耦：
`fields = {"Call_Amount": "200000", "Unfunded": "800000", "Due_Date": "2026-11-15"}`，
这些值可以被 Word 占位符、PDF 水印文案、文件名模板分别引用。

### 2.3 静态附件 Attachment

```
Attachment
├── name    : 显示名
├── path    : 绝对路径
├── scope   : all | specific | group
├── targets : [name...]   scope=specific 时的目标 LP
└── group   : scope=group 时的组名
```

解决"场景级附件所有人共享"与"某人专属附件"两种诉求的表达问题。

### 2.4 场景模板 Scenario

```
Scenario
├── name / description
├── recipients  : [Recipient]   收件人模板（每次新建事件可带出并可改）
├── pipeline    : [Step]        文档流水线模板
├── attachments : [Attachment]  附件模板
├── mail        : {...}         邮件模板
└── options     : {...}         水印/G.P.口令等默认设置
```

## 三、文档生成流水线（本次重构的核心）

### 3.1 步骤类型

不再把"Word生成""PDF水印""PDF加密"做成三个独立功能，而是统一为**流水线步骤**，
每步只做一件事，输入输出明确，可任意组合：

| 步骤类型 | 输入 | 输出 | 说明 |
|---|---|---|---|
| `word_template` | Word 模板 .docx | 每人一份 .docx | 占位符按映射替换，**格式保持不变** |
| `word_to_pdf` | 上一步 .docx | 每人一份 .pdf | Word COM 导出 PDF |
| `pdf_watermark` | 上一步 .pdf | 每人一份 .pdf | 按每人 wm_text 加水印 |
| `pdf_encrypt` | 上一步 .pdf | 每人一份 .pdf | 每人独立打开口令 + 权限口令 |
| `pdf_source` | 源 PDF | 每人一份 .pdf | 直接引入外部 PDF 作为模板/原件 |
| `static_file` | 任意文件 | 原样 | 不做处理，直接入包（可作附件） |

### 3.2 步骤链

步骤按顺序执行，**上一步的产物就是下一步的输入**（按 LP 一一对应）：

```
[word_template] → [word_to_pdf] → [pdf_watermark] → [pdf_encrypt]
   每人一份          每人一份          每人一份(带其水印)   每人一份(其口令)
```

也支持从 PDF 起手：
```
[pdf_source] → [pdf_watermark] → [pdf_encrypt]
```

### 3.3 映射规则 Mapping（每步可选）

这是"文档与 LP 的 mapping"的具体落点。每个步骤用 `mapping.mode` 声明产出粒度：

| mode | 含义 | 字段取值来源 | 典型场景 |
|---|---|---|---|
| `per_lp` | 每个 LP 一份 | 该 LP 自己的 `fields` | 催缴通知、对账单 |
| `per_group` | 每个合并组一份 | 组内首个 LP 的 `fields` | 同一中介的多个实体合并寄送 |
| `all` | 全员共用一份 | 事件级 `options` | 基金说明书、通用附件 |
| `from_sheet` | 每人一份 | 外部 Excel 数据表，按 key 列 join | 数据在 Excel、不在收件人表里 |

`from_sheet` 的 join 规则：数据表需有一列能匹配 `Recipient.name`（可配置匹配列），
未匹配上的 LP 记为 warning 而不是静默跳过。

### 3.4 占位符 ↔ 字段映射

`word_template` 步骤需要知道每个占位符取哪个值。映射来源二选一（或混用）：

- `Recipient.fields` 中的键（推荐：收件人表自带自定义列）
- 事件级 `constants`（如 `{{基金名称}}`、`{{管理费}}`，全事件通用）

**格式保持**：替换用 Word COM 的 `Find.Execute(Replace=wdReplaceAll)`，
只改文字不重建文档，字体/字号/颜色/表格/页眉页脚/分页全部原样保留。

## 四、事件执行流程

```
点击「生成全部草稿」
      │
      ├─ 1. 预检（Pre-flight）
      │     · 收件人清单非空、邮箱格式
      │     · 打开口令/权限口令齐全且互不相同
      │     · 附件文件存在性（复用现有「检查附件」）
      │     · 流水线：模板文件存在、映射无悬空占位符
      │     → 有问题：列出全部问题并中止（不生成半成品）
      │
      ├─ 2. 执行流水线（每步产出 per-LP 文件）
      │     任何一步失败 → 该 LP 标记为失败，其附件包不完整
      │
      ├─ 3. 组装附件包
      │     LP 的附件 = 各步骤产物 + scope匹配的场景附件 + 该LP专属附件
      │
      ├─ 4. 创建 Outlook 草稿
      │     合并组：组内收件人合并为一封，附件包合并
      │     主题/正文按 LP 替换 {{字段}}
      │     SentOnBehalfOfName 代发
      │     只 .Save()，绝不 .Send()
      │
      └─ 5. 写执行记录 Run
            {时间, 每个LP: 产出文件列表, 草稿状态, 失败原因, 口令指纹}
```

**执行记录可回溯**：写入 `runs/`，界面提供"查看本次产出"，并支持**只重跑失败项**
（避免全批重跑）。

## 五、界面设计（结构）

### 5.1 顶层：场景与事件

不再用标签页，改为**左侧固定导航 + 右侧内容区**：

```
┌─────────────────────────────────────────────────────────────┐
│ 文档分发助手                              [检查更新] [v3.0]   │
├──────────┬──────────────────────────────────────────────────┤
│ 首页      │  场景与事件                                     │
│ 场景模板  │  ┌── 场景 ──────────────────────────┐            │
│ 发送事件  │  │ 季度对账单   催缴通知   年度报告 │            │
│ 收件人库  │  └──────────────────────────────────┘            │
│ 设置      │  ┌── 事件 ──────────────────────────┐            │
│           │  │ 2026Q1对账单  12人  已生成  ▸ │            │
│           │  │ 2026Q1催缴     8人   草稿   ▸ │            │
│           │  └──────────────────────────────────┘            │
└──────────┴──────────────────────────────────────────────────┘
```

### 5.2 事件工作台：左侧步骤导航（不是标签页）

进入事件后，**左侧竖排步骤导航**常驻，右侧显示当前步骤内容。
功能增多时只需往左加一行，不会挤压内容区：

```
┌─ 2026Q1 对账单 ─────────────────────────────┬──────────────┐
│ ① 收件人 (12)      ← 当前                    │              │
│ ② 文档流水线 (4步)                          │  内容区      │
│ ③ 附件 (5)                                  │  （表格/     │
│ ④ 邮件模板                                  │   映射/      │
│ ⑤ 预览与生成                                │   日志）     │
├─────────────────────────────────────────────┴──────────────┤
│ [预检] [生成全部草稿]                          进度条 状态  │
└────────────────────────────────────────────────────────────┘
```

### 5.3 各步骤界面要点

**① 收件人** — 表格（横向滚动），列：名称 / To / CC / BCC / 水印 / 组 / 自定义字段(可展开列) / 打开口令。
自定义字段支持"批量列"（如一次加 `Call_Amount` + `Unfunded` 两列并批量填值）。

**② 文档流水线** — 上部步骤卡（纵向流程条，箭头连接），下部三栏映射：

```
占位符/字段          来源                预览
{{LP_Name}}      ←  name          →  Max Hill Worldwide Limited
{{Call_Amount}}  ←  fields.Call_Amount →  200,000
{{Unfunded}}     ←  fields.Unfunded    →  800,000
{{基金名称}}      ←  constants.基金名称  →  Linear Capital VI L.P.
```

每步有「输出粒度」下拉（per_lp / per_group / all / from_sheet）。

**③ 附件** — 表格：名称 / 路径 / 范围(全部/指定LP/按组) / 目标 / 存在性检查。
支持从收件人表批量导入附件路径列。

**④ 邮件模板** — 沿用 v2 的所见即所得编辑器 + 实时预览。

**⑤ 预览与生成** — 执行面板：预检结果、按 LP 的产出清单预览、生成按钮、实时日志、产出结果表。

## 六、数据存储与迁移

### 6.1 新结构

```
程序目录/
├── lp_data/                    ← 改为目录
│   ├── settings.json           全局：水印设置、GP口令、默认输出目录、邮件模板库
│   ├── events/<event_id>.json  每个发送事件一个文件
│   ├── scenarios/<name>.json   场景模板
│   └── runs/<event_id>-<ts>.json 执行记录
└── lp_data.json                ← v2.x 遗留，迁移后改名 lp_data.json.bak 保留
```

事件多时目录结构比单文件更可维护（单文件会膨胀到几万行，保存慢且易损坏）。

### 6.2 迁移方案（v3.0 首次启动自动执行）

1. 检测同目录存在 `lp_data.json` 且无 `lp_data/` → 触发迁移
2. 把现有收件人 → 生成一个默认场景「默认场景」+ 一个事件「未命名事件」
3. Word 模板与映射 → 变成该事件流水线的第一个步骤（`word_template` + `word_to_pdf`）
4. 现有邮件模板 → 事件的 mail.body
5. 现有水印/GP设置 → `settings.json`
6. 原文件改名保留为 `lp_data.json.bak`（不删除，可回退）
7. 迁移摘要弹窗告知用户

## 七、实施分期

| 阶段 | 范围 | 可交付 |
|---|---|---|
| **P0 数据层** | 目录化存储、事件/场景/收件人/附件/流水线数据模型、迁移 | 数据能存能取，v2 功能不丢 |
| **P1 场景与事件** | 场景模板、事件列表、事件工作台骨架、左侧步骤导航 | 界面骨架可走通 |
| **P2 流水线** | 六种步骤、映射规则、字段映射 UI、Word 格式保持 | Word→PDF→水印→加密 链路 |
| **P3 执行引擎** | 预检、流水线执行、附件组装、草稿生成、Run 记录、只重跑失败 | 一键出草稿 |
| **P4 收尾** | 收件人库（跨事件复用）、执行历史查看、示例数据更新 | 完整可用 |

**P0+P1 是基础**，P2/P3 才是价值主体。建议 P0-P3 一次做完（约 2 个迭代），
P4 可延后。

## 八、待确认决策点

1. **场景 vs 事件的关系**：场景仅作模板（新建事件时带出可改），还是允许事件直接引用场景
   （改场景时所有关联事件跟着变）？我倾向前者（简单、不会意外影响已发批次）。
2. **`from_sheet` 模式是否必须**：Excel 数据表 join 收件人，实现复杂度中等。
   如果业务上数据总在收件人表里，可砍掉此模式。
3. **自定义字段的录入方式**：是在收件人表里加任意列（灵活但列多时难用），
   还是预先定义"字段模板"（如催缴场景固定 Call_Amount/Unfunded）？我倾向"模板 + 允许临时加列"并存。
4. **迁移后旧文件保留多久**：`lp_data.json.bak` 保留还是定期清理？
5. **是否需要"多事件同时跑"**：当前设计一次跑一个事件（更安全）。若你要并行多个事件，需要额外做资源与进度管理。
